# Database Specification

Authority: master-plan §5, M2–M9; later authorized storage amendments are recorded below. PostgreSQL with pgvector in one instance; Prisma for supported types and parameterized SQL where required. Verification records distinguish the implemented repository schema from any applied environment.

## M21 routing storage amendment (2026-10-02)

Current M22 migration12 `20261003010000_m22_reminder_sla_escalation` adds operational observations/durable scan progress and nullable Notification linkage. Historical migrations1–11 remain byte-identical; no developer database migration. Historical M21 migration11 `20261002040000_m21_rule_based_routing` added `RoutingRuleStatus`, `RoutingRule` and `RoutingRuleRevision` only.

| Entity | Stored contract |
|---|---|
| RoutingRule | UUID; INACTIVE default / ACTIVE / terminal ARCHIVED; currentRevision≥1; version≥1; creator FK and created/updated/archived timestamps; archive status/timestamp consistency |
| RoutingRuleRevision | UUID; rule FK; positive revision; name1–120, nullable description1–500; priority1–10000; Team FK RESTRICT; bounded typed conditions JSONB; creator FK/timestamp; unique(ruleId,revision) |

Revision JSON is data only. `m21_valid_conditions` enforces exact field/operator/value keys, existing enum values, EQ one value / IN1–20, and1–10 conditions. The parent composite current-pointer FK is deferred to permit an atomic parent/revision insert. Deferred parent/child triggers enforce contiguous revisions from1 to currentRevision; no gaps, extra append or pointer rollback. BEFORE UPDATE/DELETE blocks revision mutation even through ordinary owner DML. Parent trigger fixes identity/creation fields, requires version+1, permits currentRevision unchanged or+1 and rejects changes to archived parents. Target/creator/history FKs restrict deletion. Indexes support status/list and parent/history pagination.

Runtime role has SELECT/INSERT on both tables and column-scoped UPDATE(status,currentRevision,version,updatedAt,archivedAt) on the parent. It has no whole-table UPDATE, revision UPDATE/DELETE, routing DELETE/TRUNCATE or DDL. All normal writes come through the role-authorized service; no trigger can protect against a database owner deliberately disabling constraints. Rule row locks serialize revision/lifecycle changes; expectedRevision plus expectedRuleVersion catches status ABA. Definition writes and safe AuditLog rows commit together. Evaluation uses RepeatableRead, batches target eligibility and writes no business row.

Fresh1→11, M20 10→11, M19 9→10→11 and V1.2 7→8→9→10→11 are verified only on isolated synthetic `mobiflow_m21_test`; compare all preexisting row values including seeded notes/mentions/watchers/templates/provenance and domain/AI rows. Developer migration metadata is read-only and remains7. Detailed results: [M21 verification](../v1.3/M21_RULE_BASED_ROUTING_VERIFICATION.md).

## Conventions and invariants

### M23 SavedRequestView (2026-10-04)

Additive migration13 `20261004010000_m23_saved_request_views` adds one table. Historical migrations1–12 unchanged. UUID PK, ownerUserId User FK RESTRICT, name TEXT1–80 Unicode points, normalizedName from shared NFC+trim+lowercase (retain accents), schemaVersion, filters JSONB object, positive version default1, createdAt/updatedAt timestamptz. Unique(ownerUserId,normalizedName), owner/createdAt DESC/id DESC index. No role/scope/results/counts. Single `saved-request-view.v1`; server validates version and complete JSON on write/read/apply, otherwise unavailable.

Owner User FOR UPDATE precedes identity check and count+insert in one transaction: max50 under concurrent distinct names, no global lock. Atomic expectedVersion update increments version; delete uses the same guard. Shared application normalization derives identical create/update keys, and DB uniqueness catches concurrent collisions; no second locale-dependent DB normalization. Runtime SELECT/INSERT/DELETE and column UPDATE(name,normalizedName,schemaVersion,filters,version,updatedAt) only; no owner/id/createdAt UPDATE, TRUNCATE or DDL. User deletion stays RESTRICT. Preferences need no immutable revision history. Minimal AuditLog writes share the transaction and omit names/filters/Request FK. Isolated fresh1→13, M22 12→13 and V1.2 7→8→9→10→11→12→13 preserve prior rows/checksums including M18–M22 data. Normal developer DB stays7.

### M20 operational templates (2026-10-02)

Authorized by [M20 plan](../v1.3/M20_RESPONSE_CHECKLIST_TEMPLATES_IMPLEMENTATION_PLAN.md), migration10 `20261002030000_m20_response_checklist_templates`, additive over the nine unchanged historical migrations. OperationalTemplateType RESPONSE/CHECKLIST and OperationalTemplateStatus ACTIVE/ARCHIVED are database enums. OperationalTemplate holds current searchable name/description, currentRevision and creator/time/archive metadata; names are not unique identities. OperationalTemplateRevision preserves immutable name/description/body/creator/time, itemCount and unique(templateId,revision). Ordered OperationalTemplateChecklistItemRevision stores text/required under primary key(revisionId,position). RESPONSE body1–4,000 with itemCount0; CHECKLIST no body,1–30 ordered text1–500 items. Shared schemas count Unicode code points. No arbitrary JSON payloads.

The deferred composite current FK and deferred integrity triggers enforce a contiguous revision sequence, snapshot/current metadata agreement, valid type/content, immutable declared itemCount and contiguous item order. UPDATE/DELETE snapshot triggers plus runtime SELECT/INSERT-only privileges forbid editing, deleting or appending to historical content. Templates allow only metadata/pointer/status column UPDATE; immutable identity/type/creator/time and archived lifecycle remain guarded, no runtime DELETE/TRUNCATE or DDL. Historical FKs use RESTRICT.

Optional sourceTemplateRevisionId on RequestMessage and Checklist, and manualDraftSourceTemplateRevisionId on Request, retain exact starting-point revision without changing final human content. New usage is validated ACTIVE/current under shared template lock inside existing versioned commands. A saved validated draft can be submitted/approved after later template revision/archive; Checklist copies its immutable source. Message DTOs omit source metadata; draft/checklist references project only to MANAGER. Resource-only TEMPLATE_CREATED/REVISED/ARCHIVED/USED audits contain IDs/type/revision, not bodies and no AuditLog.requestId, so no customer/AI timeline activity is introduced. No new usage analytics or notification model. Management locks the template and checks expectedRevision; concurrent revise/archive yields one success and conflict, no partial writes.

Tests use isolated synthetic mobiflow_m20_test, fresh1→10 and upgrades9→10/8→9→10/7→8→9→10 with preservation and actual privilege checks. Normal developer DB remains seven migrations; no migrate/reset/reseed. See [M20 verification](../v1.3/M20_RESPONSE_CHECKLIST_TEMPLATES_VERIFICATION.md).

UUID primary keys; timestamptz UTC instants; integer seconds/minutes for deterministic clock math; generated human publicCode unique (format `MF-YYYY-NNNNNN`, sequence allocated atomically, no count+1); text lengths enforced by schemas and suitable DB constraints. `createdAt` defaults to database time; mutable rows carry updatedAt/version where specified. Server controls IDs/actor/timestamps; foreign keys default RESTRICT rather than deleting audit/history through cascades. No business hard-delete routes. Synthetic reset is a separate explicit demo-only command in M10.

Enums are centralized in shared contracts: Role USER/STAFF/MANAGER; RequestStatus exactly the ten states in REQUEST_STATE_MACHINE; Priority LOW/MEDIUM/HIGH/URGENT; RecommendationStatus PENDING/ACCEPTED/MODIFIED/REJECTED; KnowledgeStatus UPLOADED/PROCESSING/READY/FAILED/DISABLED; SlaStatus SAFE/AT_RISK/BREACHED/PAUSED/MET. AuditActorType additionally supports AI/SYSTEM without granting login roles. Category/subcategory pairs follow AI_BEHAVIOR_SPEC.

## Transaction and integrity boundaries

- Request creation + initial history + audit + queued analysis when enabled are atomic. Manual triage cancels any QUEUED intake before acquiring its transition; RUNNING intake has AI_ANALYZING and cannot be manually overwritten.
- Approval: lock request/current review and chosen staff/team/policy/evidence generation in stable order, check versions/permissions, consume review, update request, end/create assignment as applicable, create one SLA/checklist, history, audit and notifications. External provider calls occur outside this transaction.
- ReviewKind=AI requires pendingRecommendationId and no manual pending revision; MANUAL requires pendingDraftRevision and no recommendation pointer. Only PENDING_APPROVAL holds an actionable pending reference. Enforce shape constraints plus service FK ownership checks.
- Request currentAssignee/team must agree with current Assignment for open assigned states. USER createdById and STAFF assignment roles verified against live User rows; scalar foreign keys alone cannot enforce role semantics.
- Resolve persists RequestResolution and event, freezes SLA and schedules the summary atomically. Summary retry creates a new failed/successful attempt under the same resolution provenance, never overwrites human facts. Use a unique successful summary per resolution (partial index) and at most one active run. Reopen clears currentResolutionId, cancels obsolete active summary jobs and retains prior resolution rows/artifacts.
- Intake completion validates activeAnalysisRunId and post-start contextVersion. Stale/failing run cleanup locks the current request, verifies the same active pointer/state and uses the latest version to restore NEW without discarding later messages. Completion/failure/cancel clears the pointer; stale jobs with a different current state/run are telemetry-only.
- Cancellation invalidates pending recommendation before leaving review so partial unique constraints do not block later valid work. Stale jobs cannot publish after cancellation or reassignment.
- M12 assessment tick locks Request then SLA and persists canonical state/clock version. M22 separately locks/rechecks current Request/SLA/recipients and commits immutable observation + resource-only audit + bulk deduplicated delivery atomically, without clock/business writes. Priority/reassignment/checklist/message commands retain expected request version.
- Auth refresh consumes prior credential and inserts replacement in one transaction. Replay revokes all family records atomically.

## Migration, data access and rollback policy

M1 enables pgvector/infrastructure; M2 implements baseline business schema and constraints. Vector(D) storage/index migration is M5 after a real dimension probe; RequestEmbedding is populated/queried in M6. M2 may stage vector-related tables without an embedding column; do not invent D to satisfy a schema. Every later change has a forward migration; no `db push` replacing migration history for release verification.

App DB principal has required CRUD on business tables but no general DDL; migrations use separate credentials. Append-only audit permissions deny update/delete in normal runtime. Vector SQL binds every value and uses allowlisted identifiers; no interpolation of query text. Paginate lists and bounded joins to avoid unbounded scans/N+1. Migration failure stops the gate; retain data and fix forward, never blindly reset a non-demo database. M10 demo reset verifies explicit demo flag/target and synthetic markers before destructive operations; backup/recovery of local demo data is documented there, not claimed tested now.
