## Frozen routing semantics

One `ROUTING_FIELD_DEFINITIONS` allowlist owns keys, sources, enum options, operators and normalization. One `RoutingFactsBuilder` explicitly projects only Request.category, Request.subcategory and Request.priority. Never pass a complete entity to the evaluator. Category/subcategory null stays null and cannot match EQ/IN; no draft/AI fallback. Before first approval, MEDIUM is the actual priority and classification is normally null. This deliberately limits preassignment matching to known canonical facts.

Operators: EQ (exact enum value), IN (1–20 valid enum values, deduplicated and sorted on write). No implicit case folding/coercion, null operator, arbitrary field path, free text or expressions. Conditions are a flat ordered array of1–10 and combine with AND. Repeated fields are permitted and retain AND semantics; no OR tree. Names1–120 and descriptions optional1–500 Unicode code points are inert text.

Priority: integer1–10000, lower wins. Evaluate every ACTIVE current revision; retain matches at the best priority. Equivalent target means same Team UUID. Same-target ties return MATCH listing every winning revision. Different targets return CONFLICT with no suggestedTarget. UUID ordering is only stable presentation of all equally authoritative rules, never a winner selection. No matches returns NO_MATCH with an explicit diagnostic and manual workflow remains available.

Fallback is optional in the request and is **not implemented in M21**: zero conditions/isFallback are rejected; no implicit default. Fallback uniqueness/concurrency tests are not applicable. This keeps the initial rule surface small; a later explicit amendment would be required to add fallback.

Target type is TEAM only. On create/revise/activate validate an existing active Team with at least one active/available STAFF in an active membership, reusing the existing predicate. Do not select/rank staff. Recheck targets in a single batch during evaluation. A winning rule whose target is no longer eligible yields NO_MATCH with INVALID_TARGET diagnostic, winning explanations and no actionable target; never fall through to lower priority. Conflicting top rules remain CONFLICT even if one target is invalid. Current target availability is an explicit evaluation input; the pure evaluator has no database/network/clock/random dependency.

## Storage and lifecycle

Add only migration11 `20261002040000_m21_rule_based_routing`. Historical migrations1–10 byte-identical.

`RoutingRule`: UUID, status INACTIVE/ACTIVE/ARCHIVED, currentRevision, version, creator, timestamps/archivedAt; no business definition on parent. Create INACTIVE at revision1/version1. Revision-owned definition: name, description, priority, targetTeamId FK, conditions JSONB. `RoutingRuleRevision`: UUID, ruleId, positive contiguous revision, definition, creator/timestamp; unique(ruleId,revision), deferred composite current-pointer FK. JSON is bounded/typed by shared strict contracts and a DB shape validator; no separate condition table.

Edits append revisionN+1 and increment parent version. Lifecycle commands increment parent version without changing immutable business revision. Every edit/status command requires **expectedRevision plus expectedRuleVersion**, so deactivate/reactivate cannot hide a stale lifecycle observation. Parent row lock serializes mutations; stale/archive races return409 without partial audit/snapshot writes. ARCHIVED is terminal, no DELETE route. Revisions cannot UPDATE/DELETE, including owner DML. Deferred sequence integrity prohibits gaps or extra historical appends. Parent UPDATE privileges limited to lifecycle/current pointer/version/timestamps; runtime has SELECT/INSERT on revisions, no DELETE/TRUNCATE/DDL. Target FK uses RESTRICT.

Evaluation loads at most501 active rows and rejects >500 with safe503 rather than silently truncating. This is an explicit local-demo bound, not an SLO. Lists/history keyset paginated default20/max50. Target lookup batched, no query per rule/condition/target.

## APIs, scope and provenance

All routing endpoints require live MANAGER identity/session and A01 policy, with no-store. USER/STAFF403. Scoped unknown request404; no tenant concept or fictitious foreign-manager test. Add a policy-constrained test to prove evaluator actually uses requestScope. Rule access does not enlarge request access.

- GET/POST `/api/v1/routing-rules`: strict status/q/limit/cursor; create INACTIVE.
- GET `/api/v1/routing-rules/targets`: bounded authorized eligible Team references; safe id/displayName, no users/workloads.
- GET `/api/v1/routing-rules/:id` and GET/POST `/:id/revisions`.
- POST `/:id/activate`, `/:id/deactivate`, `/:id/archive`.
- POST `/api/v1/requests/:id/routing/evaluate`: body{} or absent; reject all client facts/execute/autoAssign fields. Server loads scoped canonical fields under a consistent transaction snapshot.

Response includes MATCH/NO_MATCH/CONFLICT, diagnostic, requestVersion, normalized facts, evaluated immutable revision IDs/revisions/parent versions, winning rule names/priorities/target/explanations and nullable suggestedTarget. No timestamp/random output. Historical rule revision provides evaluation provenance. No new acceptance/provenance field is added to Assignment or the protected commands: the current command has no routing-source channel, and the final human selection remains authoritative. Do not claim a persisted rule acceptance. Final assignment retains its existing human audit and values. Routing provenance remains exclusively in manager-only evaluation/history responses and temporary UI state, absent from requester DTO/history and all AI contexts.

Safe rule audit events CREATED/REVISED/ACTIVATED/DEACTIVATED/ARCHIVED are atomic with mutation. No condition/name/description/customer content in generic audit/log. No evaluation audit, notification, scheduler or background router.

## UI and human boundary

Manager-only `/manager/routing-rules`: searchable/filterable paginated list, create/revise typed condition controls (enum selects, EQ/IN), target selector, priority, inactive/active/archive with focused confirmation, current preview and paginated revision history. Reuse existing shell/forms/styles. Keyboard labels, error/status text and visible focus; escaped React text only.

Manager NEW/TRIAGED draft and ASSIGNED/IN_PROGRESS/WAITING_USER reassignment surfaces receive an explicit evaluate card. MATCH lists winning revisions/conditions/target; NO_MATCH and CONFLICT explain manual options; loading/failure/retry do not disable manual workflow. Apply re-evaluates via the read-only API, compares the complete response to the displayed snapshot, and refuses prefill if requestVersion differs from the open form or rules/targets changed. Changed rule results must be reviewed and explicitly applied again. No automatic Request reload or retry on conflict.

Apply copies only teamId into existing draft fields, clears staff selection, focuses the staff selector and labels the applied result as a historical suggestion. Human chooses staff and may override the team. A short pending-apply lock prevents overwriting concurrent edits; core workflow stays available on failure. Actual submit continues through existing triage/submit/approval or REASSIGN with the original displayed expectedVersion. Pending approvals are reviewed via existing flow; no routing mutation added to approval UI.
